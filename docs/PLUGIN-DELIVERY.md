## 执行规则

本文件规定推进顺序；PLAN 保留每项任务的完整范围；STATUS 记录实际状态；[顺序台账](development-order.json) 记录当前步骤与门槛。任务编号是稳定标识，不按编号大小推断先后。顺序台账是步骤/依赖/状态的机器可读来源，修改时同步本文。

默认一个步骤在做，前一步完成并记录证据后开始下一步。不得因为目录已存在、页面更容易或上下文丢失而跳步。前置包的缺陷修复与当前步骤需要的公共契约增量允许开展，但必须在 STATUS 记录原因和影响，不能借此提前建设后续功能。改变顺序先更新依赖、计划和 ADR；用户新的明确要求优先。

“逐个插件”不等于互相独立到不做联调：先完成该插件在已有依赖下可验证的版本，再在下游插件到位时验证协作。未满足的跨插件验收保留待验，不把对应 P1 任务整体标 completed。D10 必须完成所有首期任务剩余项。P1-01 工作台与 P1-09 基础服务随功能补充，但初次业务实现必须先通过 D02 基础授权门槛。

## 单插件版本的完成标准

每项编码先在所属设计或 evidence 文档填写以下复用记录；后续版本若边界不变，可引用原记录并补版本探针。记录必须能定位到官方文档与公开发布包入口，不能只写“基于 Harness”。

| 字段 | 必填内容 |
| --- | --- |
| 任务与范围 | 当前步骤/任务 ID、本次可验收行为 |
| 官方能力 | 文档相对链接、精确包版本、公开入口和原生所有者 |
| 复用选择 | 直接复用 / 公开扩展 / 自有业务差异，说明选择原因 |
| 自有边界 | 仅新增哪些对象、授权、绑定、UI；哪些事实仍归官方 |
| 证据与差异 | 已有探针、待验证假设、镜像与发布版本差异 |
| 验收 | 正例、失败/取消/隔离反例、命令与尚未覆盖范围 |

Review 必须核对未重复建立 Agent loop、Skill registry/解析器、模型路由、MCP/Remote transport、Storage backend 或 Conversation renderer；出现新基础抽象时给出官方缺口证据与 ADR。产品效果参考 WorkBuddy，技术实现以 Harness 公开能力为底座。

1. 明确本版本范围、依赖、权限和剩余限制；实际实现后才添加合法 package.json/公开入口。
2. 领域服务与持久化完成；适用的 UI、Agent 工具、Remote 共用服务。
3. 具备取消/异常/授权失败等必要验证，不用无条件成功 mock 代替产品。
4. 类型检查、构建、相关测试和本地打包安装通过；记录工具命令与实际证据。真实模型和模拟测试分别标识。
5. CHANGELOG、兼容声明、数据迁移要求、安装卸载与恢复限制齐备。
6. 更新模块状态、步骤证据和任务台账；未实现模块仍保留 planned。
7. 每个 bundle 条目有稳定 Cordis `id`，必需服务使用 `inject`；安装验收必须确认 Fiber 为 `ACTIVE`，并覆盖缺失依赖的 `PENDING` 与配置错误的 `FAILED` 诊断。
8. 卸载/HMR 验收检查所有 effect、Remote、订阅、连接、定时器、watcher 与子进程达到停稳；不得保留旧服务句柄。需要顺序的异步清理在单一 disposer 中验证。
9. 工具插件同时验证 `tools`、`systemPrompt`、输入/输出 schema、原生结果持久化及注销；仅发现插件或工具名称不算可调用闭环。
10. 自有 Remote 必须由 Host 定义生成 Client 代码，使用稳定领域错误码并验证取消；设置卡 Host/Client namespace 配对，保存处理 revision 冲突。
11. 工具的规范 JSON 结果、领域回执和 UI presentation 分层；Web Client 通过公开 keyed toolview 显示并保留通用回退，PTC 调用同样经过 guard。

基础库不要求提供 UI；提供方只实现其职责，不能为满足清单制造无用页面。

## 版本策略

- 版本单位是模块；详见 [模块版本规划](MODULE-VERSIONS.md)。一个模块维护一条 `主版本.次版本` 能力线，模块内 Host、Client、Remote、资源和内置管理 Skill 同步归入该版本。页面、任务与开发切片不另起产品版本。
- 功能插件与 provider 模块独立版本化；开始实际开发时在 `modules.json` 声明 `moduleVersion`。首个可评审切片建立 `0.1` 版本线，预览制品使用 `0.1.0-alpha.N`。当前技能模块明确为 `0.1`，其制品为 `workdsh-plugin-skills@0.1.0-alpha.29`。
- contracts、ui 独立版本；破坏性契约在 0.x 阶段也必须显式记录、升级兼容声明并验证消费者，不能因未到 1.0 而随意破坏。
- bundle 有独立组合版本，交付物记录 Harness 与全部组成模块的精确制品版本及测试证据。bundle 版本不替代模块版本，也不要求未变化模块随组合包锁步升级。workspace 本地链接成功不等于发布包依赖正确。
- 用户专家/技能/项目修订与 npm 包版本分离；插件升级不覆盖用户对象。数据 schemaVersion 另行管理；回退代码不等于能回退数据库。
- 仅变更相关包；上游接口变化时识别并验证受影响消费者。未验证版本组合不宣称兼容。
- 开发版本交付默认指本地构建、打包、安装验收；npm 发布、推送、部署仍需用户授权，本顺序不是自动发布授权。
