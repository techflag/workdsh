## 一、项目定位（一句话讲清「它是什么、和 DeepSeek Harness 的关系」）

**WorkDSH = "Work + DSH"**，是一个运行在 [DeepSeek Harness（简称 DSH）](https://github.com/deepseek-ai/deepseek-harness) 之上的**产品**，而不是从零写的 Agent 内核。

- **DeepSeek Harness（主框架/内核）**：由 DeepSeek 开源、以 **Cordis** 为插件内核的 "一切皆插件" Agent 运行框架。模型、工具、技能、会话、沙箱、存储、循环、调度、UI 全部是 Cordis 插件，开发者无需改源码即可在配置层替换/扩展。官方 npm 包以 `@deepseek-ai/dsh-*` 发布，运行时可通过 `npx @deepseek-ai/dsh web` 启动。
- **WorkDSH（本仓库）**：锁定一个精确版本的官方 DSH 发布包，在其之上叠加自有功能插件（资料库、专家、技能、连接器、Office、项目、企业协作等），再以 **Desktop（Electron 外壳）** 与 **Web** 两种形态交付。

**关系结论**：DeepSeek Harness 是「主框架」，WorkDSH 是「运行其上的产品 Profile + carrier（载体）」。本仓库的二次开发目标 = 在**不修改官方核心**的前提下，向这套 Harness 运行时叠加/定制自己的功能插件。

## 三、核心机制：WorkDSH 如何「装进」DeepSeek Harness

```
┌──────────────────────────────────────────────────────────┐
│  DeepSeek Harness（主框架 / 官方 @deepseek-ai/dsh-*）      │
│  Cordis 内核：只管插件挂载/卸载/依赖；能力全在插件里        │
│   官方插件：model / tool / skill / session / sandbox /     │
│            storage / loop / schedule / UI …               │
└──────────────────────────────────────────────────────────┘
            ▲ 不修改核心，只叠加（Profile + 自有插件）
┌──────────────────────────────────────────────────────────┐
│  WorkDSH 叠加层（本仓库）                                  │
│  • profiles/shared/workdsh-features.json → 选哪些官方+自有 │
│  • packages/plugins/*、packages/providers/* → Cordis 插件  │
│  • packages/bundle → ctx.plugin(...) 注册                  │
│  • apps/desktop（Electron carrier）/ apps/web（自包含）    │
└──────────────────────────────────────────────────────────┘
```

**三个锁定层（升级时必须一起对齐）**：
1. `upstream.json` —— 官方 DSH 发布版本 + 桌面二进制 URL / Size / SHA-512（checksum 锁定）。
2. `profiles/shared/workdsh-features.json` —— 官方 bundle（`dsh-base`、`dsh-web-app`）+ 自有功能包清单。
3. 各包 `package.json` —— DSH npm 依赖通过 `@deepseek-ai/*`（Cordis 等）精确版本（见 `.yarnrc.yml` 的 `npmPreapprovedPackages`）。

**两种启动形态**：
- **Desktop**：`apps/desktop/src/workdsh-main.ts` 是唯一入口；打包脚本读取 `upstream.json` 准备并验证 Profile、官方主运行时与安装包；用官方 `runProfile` / `runCli` 接口启动同一 Host，传入可写 Profile 与安装锚点；`app.asar` 只含 Electron 入口，不含第二套 `node_modules`。
- **Web**：`apps/web` 自包含 pnpm 工作区，安装官方客户端 + WorkDSH 功能包，由官方唯一 renderer 挂载 TSX 页面。

## 四、如何接入主框架 / 二次开发（落地步骤）

### 4.1 环境准备
- **Node**：`^22.19.0` 或 `>=24.0.0`（Desktop 还依赖 `upstream.json` 锁定的 primaryRuntime：Node 24.x / pnpm 11.x / Python 3.12）。
- **包管理器**：根用 **Yarn 4.18（Corepack）**；`apps/web` 用其自带 **pnpm**（两者锁文件独立，不要混装）。

### 4.2 安装依赖
```bash
# 桌面端（根 Yarn 工作区）
corepack yarn install --immutable

# Web 端（进入其独立工作区，用自带 pnpm 锁文件）
cd apps/web && pnpm install
```

### 4.3 开发启动
```bash
# 桌面开发：build → 准备 workdsh-runtime / primary-runtime / command → 启动 Electron
corepack yarn dev

# 桌面构建 / 类型检查 / 测试 / 全量无头闸门
corepack yarn build
corepack yarn typecheck
corepack yarn test
corepack yarn check        # layout + desktop/web DSH 对齐 + web-plan + desktop check

# Web 端命令见 apps/web/package.json（其脚本独立于根工作区）
```

### 4.4 开发一个新功能插件（标准姿势，对照 `HARNESS-OFFICIAL-DEVELOPMENT.md`）
1. **建包**：在 `packages/plugins/<domain>` 新建 Cordis 插件包，导出标准 `name / inject / apply`；通过 `packages/bundle` 用官方 `ctx.plugin(...)` 注册，拥有独立子插件生命周期。
2. **UI 扩展只走官方公开 Slot**：侧栏用新的稳定 `list id`（与 `main` keyed entry 配对），右栏用 `rightbar.session`，浮层用 `shell.overlay`。**绝不替换**官方 Sidebar / Conversation / Composer / 模型设置 / 插件管理。
3. **跨插件只依赖公开契约**：类型/服务取自 `packages/contracts`，不 import 内部组件或数据表；React 组件**不接收** Cordis `ctx`、Remote service、凭据或领域服务。
4. **依赖边界**：Cordis 与官方 Harness 运行依赖用 `peerDependencies` 声明兼容边界，开发依赖精确锁定（参考 `.yarnrc.yml` 的 `npmPreapprovedPackages`）；Client bundle 的 `dsh.client.inject` 记录所需官方模块。
5. **登记模块**：在 `apps/web/docs/modules.json` 登记新模块，与 workspace、包入口、依赖、requirements 同步；默认/可选/企业激活/外置安装按 `EXTERNAL-PLUGINS.md` 边界处理。
6. **有限验收**：typecheck、build、独立安装检查完成后，再分别判定真实模型 / 界面 / 平台运行；源码构建通过 ≠ 真实运行/UI/安装验收。

### 4.5 版本与一致性闸门（升级 DSH 时）
```bash
# 1) 改 upstream.json 的版本
node scripts/bump-dsh-version.mjs
# 2) 升级前预检（不改源码/Profile，仅核对）
node scripts/preflight-dsh-upgrade.mjs
# 3) 全量闸门（含 desktop/web DSH 对齐）
corepack yarn check
```
> 版本闸门（`check:desktop-dsh-alignment` / `check:web-dsh-alignment`）不通过，**不得**打 Desktop 发布 tag。匹配产物哈希 ≠ 打包运行时验收。

### 4.6 红线（不可逾越的边界，`AGENTS.md`）
- ❌ 不得克隆 / import / 编译官方 DSH 源码；官方运行时只**提取**依赖、Office 资源、预构建命令助手。
- ❌ 不得自带第二套 DSH 安装 / 第二套 Desktop Host 或 Client。
- ❌ 不得将登录凭据、模型 Key 打入安装包（仅 `workdsh-config.json` 预设公开后端 origin）。
- ❌ 企业能力仅登录后激活，不得进个人或 Desktop 默认包。
- ❌ 新增 UI 入口不得伪造未接入的团队权限 / 业务对象 / 管理能力。

## 五、如何更新 DeepSeek Harness 主框架（升级 DSH 锁定版本）

WorkDSH 对官方 DSH 采用「**单点锁定 + 全量对齐**」策略：`upstream.json` 是唯一的版本真相源，所有 `@deepseek-ai/dsh*` 依赖与桌面二进制都从它派生并必须一致。升级不是改一个数字，而要同步 **npm 包、桌面二进制、外框补丁、运行时** 四处，并通过两套对齐闸门。

### 5.1 升级前红线

- 默认采用上游**最新正式稳定版**，经兼容性验证后升级；预发布（rc/alpha）仅在有明确产品决策时使用。
- **严禁**克隆 / 导入 / 编译官方 DSH 源码；Desktop 不得声明任何额外的 `@deepseek-ai/dsh*`（carrier 不含第二套 DSH 安装），根 `package.json` 的 `resolutions` 不得残留旧 DSH 包。
- macOS Intel（`mac-x64`）归档可因官方未发布对应 Intel 版本而停留在较早发布版（如 `rc.4`），**仅**用于 Node/pnpm/Python/Office 资源与预构建命令助手；它**不得**供应 DSH Host/Client/SDK 包，也不得改标为 `rc.5` 或做自动回退。
- `native-workbench-frame-patch` 只能改两道外框缝（恢复原生 Conversation），未知字节必须 fail closed，保留精确回滚。

### 5.2 关键配置文件（升级会触碰的地方）

| 文件 | 角色 |
| --- | --- |
| `upstream.json` | 唯一版本真相源：`version`（npm 主版本）、`desktopArtifacts`（各平台 `url`/`size`/`sha512`）、`primaryRuntime`（node/pnpm/python）、`distribution` |
| `apps/desktop/scripts/runtime-version.mjs` | 直接读 `upstream.json.version` 得到 `DSH_VERSION`（**派生量，勿手改**） |
| `scripts/native-workbench-frame-patch.json` | 锁定 `package`+`version`+`originalSha256`+`patchedSha256`+`replacements`（两缝补丁） |
| `apps/web/package.json`（`pnpm.overrides`） | 锁定 `@deepseek-ai/cordis`/`schemastery`/`cordis-plugin-*` 等运行依赖版本 |
| 各 `packages/**/package.json` + `apps/web/package.json` | 声明的 `@deepseek-ai/dsh*` 精确版本必须等于 `upstream.json.version` |

### 5.3 标准升级流程

```bash
# 0) 选定目标版本 V（必须是 npm 上已发布的精确版本；默认最新正式稳定版）
#    预发布需明确决策。先确认 @deepseek-ai/dsh 及直接/peer 依赖都已发布。

# 1) 预检 + 变更预览（dry run，不改任何文件）
node scripts/preflight-dsh-upgrade.mjs --version=<V>
node scripts/bump-dsh-version.mjs --version=<V>
#    → 报告：将要改的 pin、unexpected（既非旧版也非目标版的脏 pin）、
#       blocking（必须手改项）、review（需人工核对项）

# 2) 手动消解 blocking（缺一不可）
#    a. 更新 upstream.json.desktopArtifacts 各平台为官方发布的 url/size/sha512
#       （mac-x64 Intel 按 5.1 红线处理，仅作运行时助手，不供 DSH 包）
#    b. 重新派生 scripts/native-workbench-frame-patch.json：
#       version + originalSha256/patchedSha256 + 两缝 replacements（fail closed）
#    c. 用新归档的 runtime.json 核对 upstream.json.primaryRuntime（node/pnpm/python）
#    d. 核对 apps/web/package.json 的 pnpm.overrides（cordis/schemastery/...）
#       是否仍符合新发布的依赖范围

# 3) 应用版本改写（仅改写恰好等于旧版本的精确 pin，并改写 upstream.json.version）
node scripts/bump-dsh-version.mjs --version=<V> --apply
#    → 拒绝写回情形：某 pin 不是字面量旧版本；或写回后旧版本仍有残留

# 4) 安装依赖并跑对齐闸门
corepack yarn install --immutable            # 桌面侧（根 Yarn）
cd apps/web && pnpm install                  # Web 侧（独立 pnpm，重建锁文件）
corepack yarn check:dsh-upgrade              # npm 发布 + 桌面 feed 预检
corepack yarn check:desktop-dsh-alignment    # 桌面与 upstream 版本/二进制一致
corepack yarn check:web-dsh-alignment        # Web 全部 @deepseek-ai/dsh* == upstream.version

# 5) 构建与全量无头闸门
corepack yarn build
corepack yarn typecheck
corepack yarn test
corepack yarn check                          # layout + desktop/web DSH 对齐 + web-plan + desktop check

# 6) 打包运行时与 UI 验收（Desktop 必做）
#    准备 workdsh-runtime / primary-runtime / command → package:dir / dist →
#    启动安装包验证原生 Conversation 与 UI 通过。
#    匹配产物哈希 ≠ 打包运行时验收；版本闸门不通过不得打 Desktop 发布 tag。

# 7) 经评审的 PR 合入默认分支 main，并删除临时分支。
```

### 5.4 两套对齐闸门在查什么

- **`check:desktop-dsh-alignment`**（`verify-desktop-dsh-alignment.mjs`）：`upstream.version === DSH_VERSION`；`distribution` 必须为 `published-packages-and-desktop-release`；三个桌面二进制源必须显式锁定且格式合法（URL/size/SHA-512）；Desktop 不得声明额外 `@deepseek-ai/dsh*`（每多一个即报错）；根 `resolutions` 不得残留旧 DSH 包。
- **`check:web-dsh-alignment`**（`verify-web-desktop-dsh-alignment.mjs`）：`apps/web` 下所有 `@deepseek-ai/dsh*` 依赖版本必须全部等于 `upstream.json.version`，否则列出不匹配项。
- **`check:dsh-upgrade`**（`preflight-dsh-upgrade.mjs`）：向 npm registry 核对候选版本每个直接/peer DSH 包都已发布（https + 完整 SHA-512），并核对三个平台的桌面 feed 是否已广告该候选版本；结果写入 `.artifacts/workdsh-3.0/kernel-preflight.json`。

### 5.5 常见坑

- **脏 pin（unexpected）**：若某 `@deepseek-ai/dsh*` 既不是旧版本也不是目标版本（例如被手改过），bump 会拒绝改写并列出，需先手动归一。
- **桌面二进制未同步**：只改 npm 版本不改 `desktopArtifacts` 会被 bump 标为 blocking，且打包时会因二进制源未锁定而失败。
- **外框补丁未重算**：官方 `dsh-client-ui-conversation` 字节变化会导致 `originalSha256` 不匹配，必须按两缝重新派生，否则桌面原生 Conversation 恢复失效。
- **pnpm overrides 漂移**：cordis/schemastery 等运行依赖随 DSH 发布变化，升级后需在 `apps/web/package.json` 的 `pnpm.overrides` 中确认范围，否则可能出现双重 Cordis 实例。
