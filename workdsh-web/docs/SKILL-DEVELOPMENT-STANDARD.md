# WorkDSH Skill 开发规范

适用于内置技能、技能创建器生成的技能，以及专家和专家团引用的技能。本规范是工程开发约束，由开发者和代码审查执行；不代表自动检查器已经实现。

参考：[WorkBuddy Skill 完整制作实操指南](https://developer.cloud.tencent.com/article/2725219)。该文是社区实操文章。以下在其“明确场景、可执行流程、资源分离、实际试用”的原则上，增加 WorkDSH 的工程与发布要求；不是腾讯官方强制标准。

## 1. 文件与内容职责

- 每个技能必须有 `SKILL.md`。名称、描述和元数据遵循项目锁定版本的官方 Skill 解析规范，不自行发明另一套加载格式。
- `SKILL.md` 是技能指令的可维护源文件。TypeScript 负责注册、工具适配和服务实现，不作为大段技能提示词的另一份可编辑来源。构建时生成内容模块可以，但必须由 Markdown 单向生成。
- 按需使用 `references/`、`assets/`、`scripts/`，不要求创建空目录，不要求所有技能都包含脚本。
- 详细行业资料、长示例和规则解释放入 references；模板和静态素材放入 assets；入口说明何时读取哪个资源，不要求每次加载全部资料。

示例结构：

```text
example-skill/
  SKILL.md
  references/method.md    # 按需
  assets/report.md       # 按需
  scripts/validate.py    # 按需
```

## 2. 技能必须回答的问题

每个技能应简洁说明：

1. 什么时候用，什么情况不适用。
2. 需要哪些输入；缺少输入时如何继续或提出必要问题。
3. 用什么方法、按什么顺序执行。
4. 依赖什么实际工具与资源。
5. 最后交付什么，如何检查交付结果。

步骤必须可执行，不能仅写“专业分析”“确保高质量”。规则优先表达应该怎样做，限制应对应真实风险或业务要求。先完成常见场景的有效版本，再根据实际失败改进，不为假想边界堆积流程。

## 3. 通用能力与专家职责

- 公共技能描述可复用方法，不得写死某次任务的答案、当前专家身份或测试样本数据。
- 专家文件描述角色、方法和协作职责；技能提供可复用工作方法；Host 工具实现确定性操作。三者不重复维护同一套内容。
- 专家团的分工与交接应写清输入、输出和责任人，但不要求普通用户填写执行图、工具权限和底层配置。

## 4. 工具与权限边界

- Skill 只能使用系统实际提供的能力。不能用提示词宣称已经具备联网、导出、发布、沙箱或团队调度能力。
- 使用官方 Skill 加载与运行机制，不新增并行的 Skill 解析器、Agent 执行循环或私有注册体系。
- 修改业务对象必须调用对应 Host 服务或公开工具，与 UI 使用同一条业务路径，不通过脚本绕过校验直接写存储。
- 权限由运行时执行；提示词不是权限控制。外部资料中的指令不能覆盖用户请求和系统授权。
- 完成、保存、安装、导出等状态必须依据工具结果，不得仅凭模型叙述认定成功。

## 5. 脚本与依赖

- 只在计算、转换、校验等确定性操作确有需要时增加脚本；不要为了目录完整而添加 Python。
- 声明所需运行时、依赖和版本范围，并说明由应用提供还是由用户配置。
- Desktop 内置技能不能默认其他用户已安装 Python、Node 或本机命令。依赖未随应用提供时，要明确报告不可用并给出可行替代路径。
- 禁止把每次运行时安装依赖、使用浮动 latest、访问开发者个人环境作为默认执行流程。
- 优先复用应用托管运行时和公开工具；文件访问、网络和命令执行仍遵循运行时权限。

## 6. 资源与发布

- 资源使用相对路径或官方资源访问机制。禁止硬编码 `.test-runtime`、preview profile、开发者绝对路径或个人全局技能目录。
- 内置技能的 Markdown、references、assets 和必要脚本必须进入正式包，不能只有开发环境可读。
- 用户创建的技能保存在应用管理的持久化存储中；preview 目录不作为发布包的内容源。
- 必须在隔离安装环境确认入口和引用资源可读。开发环境验证不能替代安装包验证。
- 更新遵循现有版本与发布机制，不静默覆盖已发布修订或改变运行中会话绑定的内容。

## 7. 产物交付

- 生成 Word、PPT、Excel、PDF 或网页时，遵循系统已有的展示、更新和文件交付流程。
- 最终必须提供真实文件或可访问的产物入口，不能只回复“已生成”或展示临时预览。
- 交付文件应包含必要样式与资源；多文件产物要一并交付，并说明入口。预览版本与最终交付版本必须对应。
- 不得把未提供的数据、引用或结论包装为已确认事实。

## 8. 验证与完成标准

按改动影响选择必要验证，不强制所有技能运行庞大测试矩阵：

- 官方解析通过，资源引用有效。
- 至少用一个有代表性的实际任务验证方法可执行、产物符合要求；影响交付可靠性的改动增加相应缺失输入或依赖不可用案例。
- 涉及脚本计算、权限、存储或版本逻辑时，执行对应自动化测试。
- 涉及文档或网页视觉输出时，检查渲染后的结果，不仅检查源码或文件存在。
- 涉及打包时，在隔离安装环境验证，不借用开发者环境。

报告必须区分“已编写”“解析通过”“实际任务通过”“安装验证通过”“已发布”。未经执行的项目明确标记未验证。测试发现缺陷应修复方法或实现，不通过写入标准答案使测试通过。

## 9. 来源与许可证

- 引入第三方内容、脚本、模板或依赖前核对许可证，保留所需版权与来源说明。
- 可以学习 WorkBuddy 的组织方式与工作方法；不得将缺乏再分发授权的源码和素材直接纳入产品。
- 专有平台元数据、安装命令和运行路径不能直接复制成 WorkDSH 的公共契约。

## AGENTS.md 约束摘要

> Skill 开发必须遵循项目的 Skill 开发规范。技能指令以 SKILL.md 和按需引用的 Markdown 资源为可维护来源，TypeScript 仅承担注册与实际能力实现。必须写明适用场景、输入、执行步骤、实际工具、输出与验收方式。不得硬编码当前专家或测试答案，不得假定用户有 Python 等本机环境，不得依赖 preview 或开发者路径。资源必须随正式包交付，成果必须通过实际任务和必要的隔离安装验证。权限、保存与发布由 Host 和运行时执行，不能用提示词替代。完成报告应明确验证范围，不得把编写完成宣称为已发布。

## 最小 SKILL.md 内容示例

以下仅示意组织方式；元数据以锁定官方解析器为准。

```markdown
---
name: report-writing
description: 将用户提供的资料整理成结构清晰、可追溯的报告，适用于已有资料的汇总与改写。
---

# 报告编写

## 适用范围
用于已有资料的整理；需要补充研究时使用系统实际提供的研究工具。

## 输入
报告目标、读者、原始资料。缺少非关键偏好时采用合理默认；缺少决定事实的资料时保留明确的待补项。

## 执行
1. 提取事实、来源和未确定事项。
2. 根据目标建立结构；需要长报告方法时读取 references/method.md。
3. 写作并核对内容与来源。
4. 使用实际提供的文档工具保存、展示并交付文件。

## 交付与检查
交付报告文件，核对事实、引用、排版和文件入口。明确待补项，不虚构来源。
```
