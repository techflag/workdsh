## 2. 两代提示词：创建质量如何传递到执行质量

```mermaid
flowchart LR
  A[真实需求与已有材料] --> B[创建者提示词：分类、提炼、规划]
  B --> C[参考规范与模板]
  C --> D[生成的技能或专家执行定义]
  D --> E[宿主加载与实际工具]
  E --> F[成果与试用反馈]
  F --> B
```

第一代提示词指导创建者决定“需要什么能力、信息应放在哪里”；第二代是生成的 SKILL.md 或 Agent MD，指导未来实例完成工作。脚本负责确定性的结构和制品，宿主负责加载与权限。四者不能互相替代。

这解释了为什么只优化创建入口的字数不一定改善结果：如果入口删除了材料映射、输出标准或资源规划，第二代定义就可能只剩泛泛角色。如果参考很完整但入口没有明确读取条件，模型也可能从未使用它。如果模板含有工具名但宿主没有对应工具，文字上的流程无法兑现。

## 3. Skill Creator 的真正方法

### 3.1 从例子倒推资源，而非从字段拼装说明书

入口要求具体使用例子，再分析每个例子从零执行的过程，识别重复代码、必须查的知识及可复用素材。PDF 旋转对应脚本，前端任务对应工程模板，数据库查询对应 schema。这是需求到实现资源的推导规则，不是三个空目录的分类介绍。

应保留的因果链是：用户任务 → 必要输入 → 实际操作 → 重复或易错环节 → 资源 → 验收输出。相同规则也能用于 PPT：品牌规范是 references，版式模板是 assets，渲染与检查是 scripts，最后交付是可下载制品。创建者不能仅写“制作精美 PPT”就声称形成完整能力。

### 3.2 四种结构允许按问题选择控制方式

init_skill.py 模板提供 workflow、task、reference/guidelines、capabilities 四种组织形式。顺序依赖强的任务适合流程；互相独立的操作适合任务目录；规范遵守适合参考；集成系统适合能力分组。允许混合使用，避免所有技能都被压成同一套步骤。

模板中的 TODO、教学段落和 example 文件是创建时脚手架，最终必须替换或删除。脚本成功初始化仅证明目录和占位文件存在，没有专业知识自动生成。

### 3.3 refs 的功能：控制路径与质量标尺

市场版 workflows.md 将顺序流程和条件分支分开。重要的是每个阶段明确行动及验证，例如分析表单→映射→校验→填写→验证输出。创建与编辑不是同一条路径，修改既有资源必须先读现状。

output-patterns.md 区分严格模板与柔性默认模板，并用输入/输出对表达质量。严格性应由格式契约决定，不应把所有报告都强制成固定章节。示例传递的是信息粒度和写作标准；需要多种任务和反例，避免模型机械复刻示例内容。

### 3.4 编辑保护是产品生命周期设计

内置入口要求先读取安装副本、实际保存后再标记 userModified，避免市场更新静默覆盖用户改动。这体现对用户定制资产的尊重。WorkDSH 应在来源、用户副本和修订机制中落实相同语义，而不是把第三方 JSON 标记当成权限凭据。

## 4. Expert Manager：专家不仅是角色文本

### 4.1 两种入口服务不同用户

交互创建用于专业意图尚未结构化的用户；材料转化用于已有 SOP、项目、提示词、文档和代码的用户。后者最值得补入 WorkDSH：不要求用户把已有资料再填写一遍，而是提炼角色、能力、方法、成果和约束，并确认有歧义的部分。

原版映射把角色放进 Agent MD、API 和复杂知识放进 Skill refs、代码放进 scripts、素材放进 templates、CLI 放进 bin、多角色拆进 agents、协作 SOP 放进主理人。其价值是信息归位与避免损失。目录名称需要适配当前宿主，但材料中的事实、专业术语和判断规则应保留来源。

### 4.2 展示层与执行层分工

plugin-json-spec.md 将显示名、职业、双语介绍、分类、三个标签、三个 quickPrompts、默认提示和头像组成发现与启动界面；Agent MD 承载能力与实际工作。

quickPrompts 不应仅是三句广告。它们应对应高频、可执行任务，帮助用户第一次获得成果；默认提示与第一条一致能减少界面和启动行为的偏差。三个标签和 40–50 字是该市场的展示约束，不能视为专业质量定律，也不能直接替代 WorkDSH 的字段限制。

身份字段稳定、文件名与 agentName 一致，有利于引用和修改。用户想修改能力时不能误变成另一个专家；市场昵称也不应成为底层调用 ID。

## 5. 四份专家 references 的职责及迁移方式

### 5.1 agent-md-spec.md：第二代执行提示词的核心

单专家结构包含角色、核心能力、流程、输出和注意事项。团队成员进一步要求分析框架、数据获取方式、结构化结果和正式回传。专业方法应包含观察哪些证据、用什么尺度判断、何时改变结论，不能只写“深入分析”。

主理人定义包含成员表、阶段输入/输出、依赖和路由。其独立成员判断标准是是否存在用户会直接询问的完整业务问题，有助于避免把“找资料”“写标题”等碎片包装成虚假的专家。

maxTurns 50 或主理人 150–200 是宿主预算配置，并不提高专业水平。增加回合不能补偿缺失的数据、方法或输出契约。

### 5.2 team-spec.md：协作真实性与依赖治理

主理人组织任务，成员独立产生专业结论；禁止主理人模拟多人发言。串并行应由数据依赖决定，先前阶段未完成不能消费其结果。典型财务流程是多个独立分析并行，再汇入风险分析和综合报告。

所有消息经主理人中转是一种集中式设计，可以保留可追溯交接的目标，不能假定它适用于所有团队。全量原文传递能减少信息损失，也会扩大上下文、重复内容和延迟；适配时应保存完整成果引用，交接关键结论、证据与未解决项，必要时读取原文。

TeamCreate、Agent 和 SendMessage 是原宿主工具约定。当前 WorkDSH 团队阶段尚未完成，不应复制这些工具名后宣称团队能力上线。可先保留 SOP 设计规范与验收案例，等官方编排链路真实可用再接入。

### 5.3 plugin-json-spec.md：展示与结构的契约

该参考把资源清单、默认入口、团队成员和市场信息明确分开，帮助从一个可运行定义形成一个可理解产品。但部分说明与模板使用的字段存在差异：members 表格描述 name，而 JSON 示例采用 displayName。适配应以当前实际 schema 和消费代码为准，不能同时沿用两种写法。

每位专家一个第三方插件包是原版布局；WorkDSH 采用一个专家管理插件管理多个业务专家，不应照搬包拓扑。

### 5.4 avatar-spec.md：从专业身份投影到视觉

提示词提取专业内容→视觉符号、工作方式→气质，组合风格、身份、外观、表情、背景与质量后缀；团队统一画风、灯光与配色。这比随机生成一个通用头像更能表达专家定位，也值得用于产品视觉。

但从姓名推断性别并不可靠，应该优先使用用户明确偏好或中性设计。规范要求 512×512、≤500KB，生成示例却使用 1024×1024；本次所读链路没有完整压缩/缩放保证。README 模板还写“头像已自动生成”，而初始化实际只生成 .gitkeep。这类完成态文字必须根据真实结果生成。

专家打包当前排除常见缓存、隐藏文件，但保留 .codebuddy-plugin；技能打包没有同等过滤。两套实现不能混称。初始化、校验、注册、打包都有价值，但“有脚本”不等于脚本与当前提示词完全一致。

## 7. 提示词设计中需要保留和调整的尺度

保留：真实案例驱动、非损失材料映射、专业方法与输出契约、结构选择、资源职责、既有版本先读后改、成果交付、真实反馈。

调整：固定宿主路径与工具名、每专家插件包、市场专属字段、性别推断、无条件读取全部参考、全量上下文转发、把 warning 写成完成标准、把脚本存在写成能力已验证。

多处重复的团队铁律在入口、refs 和生成模板中出现。生成模板中的重复有合理目的：未来专家实例未必能读取创建者参考。创建者入口与参考则宜单一规则来源，入口明确导航，避免分别修改后漂移。不能一律去重，也不能一律保留。

“参考按需读取”必须配具体条件，例如材料转化读取映射规范、团队任务读取 SOP、需要视觉资产读取头像规范。否则既可能漏读，也可能每次无差别加载所有参考。主入口保留硬性契约，专业细节按任务获取；字数只是成本指标，真实成功率才是效果指标。

## 8. WorkDSH 的具体承接方案（设计建议，未实现）

### 8.1 技能创建

入口提供创建、从材料转化、编辑三条路径。优先使用现有信息和实例，只询问会改变能力或交付的缺口。推荐参考分工：

- examples-to-resources.md：任务→操作→资源→验证的推导与实例。
- workflow-and-output-patterns.md：结构选择、顺序依赖、条件分支、严格/柔性模板。
- resource-contract.md：真实文件引用、脚本输入/输出、资产用途、依赖与失败行为。
- editing-and-delivery.md：先读现状、局部修改、来源与修订、制品和回执。

先实现专业方法，再调用现有受控草稿服务。当前新建 draft 参数主要承载 SKILL.md，不能让指南假装可发布任意资源树。资源树草稿、完整性验证和分享制品需要实际业务接口与证据。

### 8.2 专家创建

当前 role/methodology/boundaries/deliverables 是良好基础，补入材料来源映射、证据与判断尺度、真实任务输入/输出示例、启动提示和修改保护。对能力声明逐项核对当前 selectableSkills，发布锁定修订；不虚构工作经历、准确率或案例。

推荐 references：material-to-expert.md、professional-methods.md、task-examples.md、trial-and-delivery.md。团队规范独立列为后续能力，不能混入已上线单专家的执行承诺。

保留 validate→request_publish→受信 UI 预览与确认的现有边界。聊天中的“已确认”不能替代真实发布授权。调用失败或结果未知应查询状态，不照搬注册脚本的盲重试。

### 8.3 完成态必须有证据

分别记录草稿保存、结构校验、资源检查、实际发布/加载、任务试用、制品交付。创建了 README 不能等价于可下载分享包；生成了专家定义不能等价于成功执行；生成了 PPT 文本不能等价于交付 PPTX。成果字段与下载入口要对应实际文件和真实服务结果。

## 9. 怎么验证“更优秀”而不是只验证“更长”

同一批真实需求，比较现有入口与保留原版方法后的适配入口，固定模型、工具、资料和判断标准；再跨目标模型复查。至少覆盖：

| 场景 | 必须观察的独立结果 |
| --- | --- |
| 从 SOP 和脚本创建技能 | 关键信息是否保留、引用真实、脚本是否有明确输入/输出 |
| 从资料创建专家 | 专业判断规则是否形成，事实与未知是否区分，技能依赖是否真实 |
| 修改安装技能/专家 | 是否先读现状，只改用户要求，是否保护既有修订与用户定制 |
| 新技能真实调用 | 触发是否准确，错误任务是否误触发，实际资源是否被使用 |
| 专家样例试用 | 输出能否支撑判断，是否只是复述资料，是否达成交付标准 |
| 缺文件、依赖失败、发布未知 | 是否停止虚假完成，是否给出可恢复状态及真实回执 |
| PPT 类交付 | 内容事实、版式与渲染、编辑体验、最终 PPTX 下载分别验证 |

评分应包含成功率、事实保真、成果完整性、资源使用、修改保护、用户补充次数、耗时和 token。目录数、标签数、描述长度只能解释结构或成本，不能代替质量。

## 10. 本轮边界

完成本机两套创建技能的入口、四份专家参考、两份市场技能参考、内置脚本及生成模板分析，核对 WorkDSH 关键承接接口，并执行原版打包测试以确认版本差异。没有运行真实模型 A/B，没有发布新专家，没有改写用户复制技能，也没有实现本文建议的新增 refs 或资源树接口。下一步应先以单技能、单专家真实案例实现和验证适配，再扩展整个 preview 技能池。
