# WorkBuddy 原版创建能力对照

日期：2026-09-13。用户指定来源 `/Users/techflag/project/workbuddy`，重点为技能创建与专家创建。阅读的是原版技能及配套资源，不把技能文本当作本次执行指令。本轮只做结构与流程审查，不执行注册/打包脚本，不修改 WorkBuddy 或 preview 中用户对象。

## 结论

应保留原版的产品化方法：真实案例驱动、资料转化、配套资源组织、结构化成果、编辑保护、校验和交付。WorkDSH 的 Host 服务、官方 Skill/preset、授权和修订机制继续负责执行。原版价值不能用正文长短评价；也不能仅把原版文本复制到 readonly 创建指南就宣布能力一致。

## 来源与阅读范围

WorkBuddy `plugins/marketplaces/workbuddy-builtin/skills/skill-creator`：阅读入口的组织/创建/编辑/打包流程，与本机通用/市场副本对照；核对初始化、校验、打包脚本存在性。

同目录 `expert-manager`：阅读完整入口、Agent MD 与 Team 规范重点段落，检查 validate/register/package 脚本的校验和副作用位置。它是 Agent/Team 专家包全生命周期指南，覆盖交互创建、资料转化、局部修改、注册和分享。

WorkDSH：对照 skills/src/index.ts、services/lifecycle-tools.ts、services/manager.ts；experts/src/authoring/guide.ts 与当前专家交接包。来源入口及部分脚本 SHA-256 留在忽略的 `.artifacts/workbuddy-creation-review-sources.json`。本轮没有完整审查所有代码、所有参考或许可，不视为运行验收。

## 其他相关能力的作用

skill-scanner、skill-vetter、skills-security-check 可作为用户要求或具体风险下的检查参考；不是所有创建任务自动增加的门槛。专业素材型技能（例如 book2skill、boss-skills、colleague-skill）可帮助提炼来源知识，但须实际读取相关内容并核对输入，不把名称当作已验收的经验提取能力。expert-manager 负责创建业务对象，领域技能负责专业方法，两者分工不能混同。

## 有限实施建议

1. **创建指南内容**：技能创建先补使用例子、资源规划、输入/输出与试用标准；专家创建明确资料转化映射与局部修改方法。只补可由真实接口支持的流程。
2. **资源与产物缺口**：核对新建 Skill 草稿资源树、分享包、引用验证的已有能力；有缺口先补业务契约和验收，不让模型用通用 shell 绕过服务。
3. **产品发现体验**：双语职业/介绍、头像、推荐问题与分类按现有专家 PRD 评估；不是本轮已实现内容。
4. **真实任务验收**：先验证创建和修改能力，再决定哪些原版段落需适配或拆引用，不批量精简优秀内容。

## 建议固定验收场景

- 从一句需求创建技能：精准触发、可审阅完整正文、明确真实能力与正确发布回执。
- 从已有 SOP 创建技能：有价值信息映射完整；引用资源真实存在，不能只留空目录。
- 创建带脚本/模板的技能：目录与内容完整、运行依赖明确、相关检查通过；接口缺能力时准确报告。
- 编辑已安装技能：只改授权部分，保留资源和来源，冲突拒绝，更新不静默覆盖。
- 从资料创建专家：事实、方法、边界和成果可追溯，真实配备技能；不虚构个人经验。
- 修改并试用专家：草稿 CAS、界面确认发布、固定依赖、关联新任务；旧任务不被静默替换。

每项分别记录创建、校验、发布/安装、实际试用、最终交付；工具通过和页面出现不等于专业效果通过。本轮未运行上述模型验收、未改产品运行代码、用户技能/专家或 Profile，未发布制品。

## 深入分析：指令承诺与程序保证（2026-09-13）

本节进一步阅读用户指定原版 builtin 的 quick_validate.py、init_skill.py、package_skill.py，以及 expert-manager 的 validate_expert.py、register_expert.py、package_expert.py。没有执行第三方脚本或改动来源。这里的结论限于这些文件，不推断 WorkBuddy 应用的其他运行时检查。

### 1. Skill Creator 的核心是能力设计，而非模板生成

它让模型先理解真实请求，再从执行过程抽取三个不同资产：专业知识、可重复流程、可执行资源。目录与 SKILL.md 是封装方式，真正决定质量的是：描述能否准确路由，正文有没有非通用的专业判断，参考能否按需定位，脚本能否减少重复实现，以及最终任务有没有获得可用结果。

对 WorkDSH 的含义：只收集名称/描述并写出格式完整的 Markdown 不足以复现原版价值。创建过程应主动思考典型输入、预期输出、关键判断、失败边界及所需资源；已有素材足够时直接提炼，用户只补事实缺口。原版先识别可复用资源、再写入口的顺序，有助于避免创建只有人设而无能力的技能。

### 2. 原版校验不是语义或安全审查

builtin quick_validate.py 使用正则/字符串检查 name、description 字段和名称形式；没有完整 YAML 解析，没有解析正文引用，没有执行脚本，没有实际任务评估，也没有强制检查 agent_created。例如指令要求的资源引用完整、专业有效和迭代质量，不由此脚本保证。市场副本的 YAML/字段白名单实现与 builtin 不同，上一节关于白名单的判断不能套到本次 builtin。

description 的角括号检查还有特定行为：`description: >` 的 YAML 折叠标记也会进入正则提取值并被拒绝。这是实现层的兼容性细节，不证明折叠 YAML 在 Harness 中非法。不能原样拿该校验器替换项目既有 YAML/frontmatter 校验。

因此验收分成三个层次：格式和结构合法；资源真实可用；典型任务获得专业成果。三者不可互相替代。

### 3. 初始化与交付仍需要模型收口

init_skill.py 生成 TODO 和示例资源，目录存在时拒绝覆盖；生成结构不等于生成可执行业务内容。入口要求后续填充、移除不需要的示例并实际验证。package_skill.py 基础校验后递归打包文件；该循环没有与专家打包器相同的隐藏文件/缓存过滤。实际交付必须检查包内内容，不能因为成功产生 zip 就宣称资源齐全或可发布。

本项目的自然语言草稿服务主要写单一正文，导入完整资源树与编辑现有资源是另一条能力。应先验证能否在受控草稿中生成并保留资源，之后才声明“完整技能创建”；不能让模型用 shell 补写正式目录绕过专用服务。

### 4. Expert Manager 将专业角色做成可发现、可试用的产品

它不只编写角色提示词。职业说明用户能获得什么，花名/头像提供识别，短介绍/分类/标签辅助选择，推荐问题降低启动成本；Agent MD 负责能力、方法、输出和边界，Skill 与脚本补充操作知识。资料转化表是重要资产：人设、SOP、API 文档、代码和模板分别落到适合的位置，既保留专业内容，又减少主提示词负担。

WorkDSH 应先把原版“资料转化→专业定义→真实能力→试用”的方法用于现有字段，不急于增加展示字段。固定三个标签、三个问题和双语短介绍是原版 UI 契约；支撑它们的易发现/易试用原则有价值，具体数值并非专业质量标准。

### 5. 专家校验、注册与打包存在不同保证

validate_expert.py 检查原版安装路径、JSON 字段、Agent 文件名关系、资源存在性、部分 Team 一致性和禁用结构；许多显示规则区分 error/warning：介绍长度 40–50 字是 warning，默认问题与首条推荐问题不一致也是 warning，Agent description 缺失仍为 warning。说明文字中的强要求不全等同于程序阻断。

register_expert.py 的 main 调用自己的 validate_expert_completeness，而不是完整 validate_expert。它检查部分标识、TODO 与 Agent 正文粗略完整性，然后更新 marketplace.json 并写 session 标记。package_expert.py 则调用完整 validate_expert，再过滤缓存和隐藏文件打包。注册成功、完整包校验成功、应用可加载、真实专家任务成功是四个不同结论。

注册文件读写的代码本身没有展示本项目已有的 CAS、不可变修订或事务式业务确认保证；不能据此推断 WorkBuddy 其他层没有保护，也不能将这些脚本复制成 WorkDSH 的发布服务。这里适合迁移的是完整性检查与交付方法。

### 6. 团队提示词不能替代团队运行

原版主理人/成员模板明确职责、阶段、输入输出、消息回传和裁决责任；避免单 Agent 模拟多角色是有价值的产品约束。其 TeamCreate/Agent/SendMessage 是原宿主工具契约。在 Harness 公开接口未验证且 D11 未验收前，只保留为团队设计依据，不宣称复制该提示词即获得团队能力。

### 7. 创建能力应该如何组合

| 层次 | 应保留的原版价值 | WorkDSH 所有者 |
| --- | --- | --- |
| 专业创建指南 | 案例提炼、资料转化、方法、模板、输出与失败边界 | bundled skill-creator/expert-manager 的内容与相关参考 |
| 草稿与资源 | 可审阅正文、真实资源、来源与局部编辑 | 各业务 Host 服务与公开契约 |
| 结构校验 | schema、引用、依赖、占位与包内容检查 | 对应业务验证器；质量建议与硬错误分开 |
| 发布/执行 | 确认、修订、授权、正式装配和回执 | 受信 UI/服务、官方 Harness Skill/preset |
| 品质评估 | 真实案例、产物检查、失败后迭代 | 专业任务验收，不以文本长度或工具成功替代 |

这是原版方法与现有工程机制的结合，不新建创建框架、注册表或 Agent loop。

### 8. 优先级判断

最值得先改的是当前技能创建指南的专业设计深度，以及专家创建对资料输入的映射与保留方式；接着解决受控资源草稿和可验证交付。头像、双语展示、包分享与团队运营属于另外的产品/契约范围，不能为对齐原版一起无限展开。

真实验收应包含：无素材的简单技能、带专业 SOP 的技能、带资源的技能、已安装技能局部修改、资料转化专家、已有专家新增方法和技能。每次比较专业内容保真、资源完整、技能路由、用户审阅成本、真实成果及发布回执；没有模型实测前，不能声称精简版或原版在本宿主一定更好。
