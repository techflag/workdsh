# 统一内容操作 API 架构审查

日期：2026-09-12。被审查文档：UNIFIED-API.md（原157行版本）。初次结论：需要修订后再作为实现契约；统一工具入口与分类型适配的方向保留。以下保留原审查与原行号，修订处置见末尾；原行号不对应新版位置。

交叉依据：AI-EDITING.md、ADR-0024；当前Office的client-only实现；锁定Harness镜像的storage、sidebar-right、工具编写说明。没有运行实现代码或真实模型测试；以下故障场景是验收要求，不是已复现产品事故。

## R01 / P1：尚未定义能同时承接人工与AI操作的权威内容模型

位置：UNIFIED-API.md 121行、143—149行，关联82—89行。

文档要求Host执行确定性操作、保存完整状态，又让人工编辑从各原生SDK转成同一组操作；但未确定持久化的是规范化语义模型、原生SDK快照，还是带扩展字段的组合。现有操作只覆盖有限语义，原生编辑器还能修改文字样式、段落分割、合并、粘贴等。比如用户给一句话加粗后，下一次AI插段触发重载：如果Host模型不保存富文本run，格式就会消失；若直接接受任意厂商快照，又没有统一校验和稳定ID保证。

修订：先为首期document确定版本化持久模型、稳定blockId/run标识、受支持富文本属性及未知字段保留规则；明确AI语义操作与UI SDK事务如何转换、哪些原生按钮首期不可用。适配器必须在候选真实SDK上证明双方往返不会丢失已有内容。六类不必统一内部模型，但每类必须有唯一、可版本化的权威模型与能力范围。

验收：手动加粗/中文输入法/粘贴/分段后AI插入段落，内容、样式与选区处理符合约定，保存刷新后仍一致。暂不支持的操作在UI显式限制。

## R02 / P1：状态、修订与幂等回执的原子提交缺少可落地存储方案

位置：UNIFIED-API.md 42行、59—72行、121行；AI-EDITING.md 49—55行。

Harness storageDomain的逐领域写链保证单次put/update持久化与通知，不等于跨表事务（subsystems/storage.zh.md 126、153行）。若先写内容再写回执，中间崩溃，重试同operationId会重复插入；反向顺序则可能返回成功但内容未写入。这会破坏实时写作、取消后恢复与幂等承诺。文档也未规定重试查询先于旧baseRevision冲突检查。

修订：明确一个提交点，例如在单文档记录中用一次KvTable.update原子保存新状态、修订及去重回执；检查同主体operationId与摘要后再判baseRevision。若选择不可变版本+head，定义写入顺序与崩溃恢复。创建阶段尚无documentId，另定主体+组织+操作名+operationId的去重键。规定回执保留策略，超期不允许静默重放旧操作。

验收：持久化前失败、提交后回执丢失、重启后同ID重试、同ID不同参数、同revision并发写，分别不出现重复段落或虚假成功。

## R03 / P1：没有已有文件进入统一文档身份的入口

位置：UNIFIED-API.md 31行、39—44行、129行。

create只能新建；read/edit/present都要求documentId。用户从现有右侧Tab打开的DOCX/PPTX/XLSX只有资源地址，尚未定义如何建立工作副本和documentId。于是这套接口可以演示新建文章，却接不上本次最初要求的已有Office产物。同一文件重复打开是否产生多个互不更新副本也未定义。

修订：提供content_open或扩展content_create的严格source分支（kind与source互斥、返回实际识别类型），只接受授权resourceRef；明确原始版本/哈希、导入能力、稳定文档ID映射和显式fork语义；给出重开/新任务如何从资源获取documentId。不要让AI猜文件路径或从界面标题推断ID。

验收：UI与AI打开同一已授权资源得到同工作副本；源文件外部变化触发冲突；不支持/加密文件有确定错误；无跨主体副本复用。

## R04 / P1：快照与订阅未形成无丢失衔接，展示请求未绑定目标客户端

位置：UNIFIED-API.md 20—21行、43行、126行、133—137行。

文档写了重连取快照与缺口重取，但没定义首次快照和订阅的边界。如果先读修订5，再订阅，期间的修订6漏掉且之后无新事件，客户端永远停在5，不会检测到缺口。Harness domain/changed只是进程内通知，需要明确跨Connection的传递和水位规则。另一个浏览器当前查看会话B时，会话A的content_present不能直接调用全局当前sidebarRight：官方写操作作用于已挂载Session，可能打开到错误会话或抛错（sidebar-right.zh.md 73—89行）。

修订：选定官方Client model/Remote或Connection公开机制，定义订阅登记→快照水位→增量过滤的顺序，或有确认游标的受控轮询；包含最后水位核对、撤权、卸载与重连策略。展示请求携带Host解析的sessionId、requestId、documentId、revision与到期时间；客户端只处理对应会话并回执appliedRevision，用户未打开该会话时返回queued/CLIENT_REQUIRED，不偷换当前会话。

验收：注入快照/订阅间唯一一次写入，页面最终必须到最新修订；A/B会话与两浏览器不会串页；撤权停止读取；无需后续写入触发恢复。

## R05 / P1：指定修订导出没有不可变输入和幂等作业契约

位置：UNIFIED-API.md 44行、121行、127—129行。

export宣称输出指定revision，但只要求保存完整已提交状态，没有定义历史修订保留或导出时固定输入。AI继续写到revision9、浏览器才执行revision8导出时，如果使用正在编辑的SDK实例，返回的文件可能实际上是9甚至包含尚未提交的人工内容。导出没有operationId，连接中断重试也可能重复落盘。CLIENT_REQUIRED只描述无客户端，没有处理客户端在导出途中关闭。

修订：导出开始时固定不可变快照/源哈希和adapterVersion，给定请求内revision不可得时返回REVISION_UNAVAILABLE；使用独立只读导出实例，不取当前编辑缓冲。添加幂等exportRequestId、作业状态、授权目标/副本策略、文件哈希与revision回执；客户端失联或结果不确定可查询并恢复。可先只允许导出当前修订，但在受理时必须固定它。

验收：导出8期间编辑到9，文件内容仍对应8；中断重试只得到同一回执/副本；没有客户端或转换不支持时不虚报成功。

## R06 / P2：人工输入与持续AI提交可能导致无限冲突

位置：UNIFIED-API.md 135—137行。

整文档baseRevision保护了不覆盖，但AI持续逐段提交时，用户输入缓冲会不断过期。当前只写“显示冲突、重新读取后决定合并”，没有谁暂停、输入法提交边界、自动保存时机或冲突解决动作，实际用户可能每次保存都冲突。原生撤销栈也可能撤销了远端变化而非自己的操作。

修订：首期选择明确交接策略，例如本地编辑开始后暂停该文档的后续AI提交并提示等待人工提交/取消，或支持安全的非重叠操作重放；有界等待与恢复要明确定义。中文IME组合期间不提交中间文本。撤销通过服务提交有前置条件的逆操作，拒绝回滚整篇旧快照；明确每个用户的撤销历史。

验收：AI循环追加期间用户修改第二段，能在有限步骤内完成保存并让AI继续；不丢字、不重复段落，不把其他编辑者内容撤掉。

## 建议修订顺序

1. R01+R03：确定文档身份、数据模型及已有文件入口。
2. R02+R04：实现并验证原子提交、幂等、正确会话的页面同步。
3. R05+R06：固定导出输入，补人工交接与撤销。

保留6个简洁工具的目标，但不为固定数量遗漏已有文件入口；可以把open/new设计为同一工具严格联合。完整六类能力仍在范围内；上述契约先在文档纵向闭环通过后推广。
