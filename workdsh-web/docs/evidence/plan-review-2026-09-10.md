# 开发计划修订 6 审查

日期：2026-09-10。审查对象：PLAN、PROJECT-DESIGN、research/workbuddy-core-domains；交叉检查 CONTRACTS、TEAM-DESIGN、ACCEPTANCE、COMPATIBILITY。仅文档审查，不是 Harness 实测或产品漏洞复现。

结论：架构方向可继续用于 P0 探针；作为 P1 完整实施基线仍需修订。以下 6 项均未修复，本次保留原方案供核对。

## R01 [P1] 连接实例 ID 不能锁定实际执行账号与目标

位置：PROJECT-DESIGN.md 第 36 行；PLAN.md 第 95—99 行。

任务固定“具体连接实例”，但实例允许更新，未定义配置修订和外部账号身份的稳定性。若同一实例从测试地址/账号改成生产地址/账号，恢复的旧任务仍引用相同 ID，可能在新目标执行写入；不跨实例回退的约束无法阻止此问题。

建议：绑定 connectionId、configRevision、外部账号身份标识/目标指纹、已授权工具范围；同账号凭据轮换与账号/目标变更分开处理。前者按提供方规则刷新，后者令旧绑定失效并显式重绑定。调用前重查授权，绝不把明文密钥放入快照。

验收：执行前暂停、修改实例地址或账号、恢复，必须阻止静默提交；同账号正常凭据轮换另测。

## R02 [P1] 交接摘要缺少可执行的信息访问控制设计

位置：PROJECT-DESIGN.md 第 48 行。

文档要求接收人无权读取的内容不能通过摘要转移，但只规定了目标访问检查。若在原会话中生成摘要，模型已接触发送人的私有资料、个人连接查询结果和历史工具输出。仅过滤附件引用或新会话权限无法防止摘要携带这些信息。J05/J06 定义了结果，却未给出生成摘要的可信输入边界。

建议：建立交接资料清单与来源/共享授权；在独立干净上下文中仅使用接收人获准访问的资料生成摘要。无法识别来源的原会话摘要默认保持私有，或者经明确的内容分享授权作为独立资产发布；不能依靠提示词要求模型自行排除秘密。创建及交接领取时重查权限。

验收：原任务含接收人不可读的标记信息，交接包、摘要、日志和新任务均不得含该信息；撤权发生在准备与领取之间时交接失败。

## R03 [P1] MD 审阅可能被原生文件写入路径绕过

位置：PLAN.md 第 201 行；research/workbuddy-core-domains.md 第 21 行。

方案定义 propose/accept 服务，但没有规定资料库权威正文与 Agent 可写工作区的物理关系。若库文件以可写路径提供给支持写文件/脚本的 Agent，后者可直接改正文，绕过建议、审批、expectedRevision 和审计。现有 HTML 不获 Host 权限的约束不覆盖这条路径。

建议：权威资产存储不作为 Agent 可写目录暴露；任务得到只读修订或可写工作副本，提交变化必须进入建议修订服务。将文件路径、符号链接及脚本写入保护加入 P0 能力验证；公开隔离机制不支持时，明确限制可用写入能力。

验收：原生文件工具和脚本直接覆盖、重命名替换、符号链接访问都不能修改权威正文；建议接受后正文只产生一次新修订。原始创建与修改既有正文分别定义。

## R04 [P2] Web 客户端生命周期被用作自动化执行条件

位置：PLAN.md 第 158 行。

Web 架构已经区分 Host 与 Client，但自动化规则写成客户端关闭就不执行、重开恢复。浏览器关闭不代表 Host 停止；多标签、多设备甚至无法给出唯一的“客户端关闭”时刻。如果按页面启动调度，会造成漏跑或重复恢复。

建议：明确由单一 Host 调度所有者持久管理触发；浏览器仅配置和订阅。Host 停止/重启才进入错过触发处理；如果产品刻意要求在线页面触发，需明确唯一租约及在线语义。未来多 Host 再引入调度租约，避免首期超范围。

验收：关闭标签但 Host 在线、多标签同时打开、Host 停机跨过触发点、重启恢复，分别有确定结果。

## R05 [P2] 首期交接的可交付主体范围不明确

位置：PROJECT-DESIGN.md 第 48、52 行；研究记录第 23 行。

P1 交接包含“接收主体”，但 P1 只有本地单用户提供方；实际邀请和多人入口在 P3。当前无法判断 P1 必须提供跨用户交接 UI，还是仅同用户切换专家，并通过测试提供方验证跨主体服务。J06 同样没有区分，会使首期验收与实际可用产品错位。

建议：明确 P1 用户可操作范围为同主体专家交接，跨主体服务用预置测试身份验证；P3 再开放成员选择、交接接收和通知，或将真实跨主体入口及必需身份能力明确前移。无论哪种选择，都不能把双主体测试当作用户已可使用的团队交接。

验收：分别定义 P1 UI、P1 多主体集成、P3 真实交接三个独立用例及入口依赖。

## R06 [P2] 验收编号混合阶段，无法可靠计算首期完成

位置：PROJECT-DESIGN.md 第 66 行；PLAN.md 第 189 行；ACCEPTANCE.md 第 77—80 行。

项目设计要求 J01—J10 全通过，而计划要求其中 P1 项通过。J07/J10 单个编号又同时包含 P1/P2/P3 行为。实现者若把 J10 标完成，会掩盖未实现自动化/邀请；若坚持整个用例完成，则 P1 被后续阶段阻塞。团队验收也存在“首期必测”标题下包含后续实际 runtime 的情况。

建议：每条验收只有一个阶段与状态，如 J10a/J10b/J10c，独立任务/证据引用；统一 P1 发布所需集合。检查器验证阶段和任务映射，而不只检查编号文本存在。

验收：机器可列出所有 P1 阻塞项；未完成的 P2/P3 测试不阻断 P1，也不能被 P1 检查标为完成。
